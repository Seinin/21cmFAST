# Design

## 一、范式声明（本变更的核心交付物）

先把四条已定的决定写成可评审的契约，再谈落地。**评审通过前不写实现代码。**

| # | 决定 | 内容 |
| --- | --- | --- |
| 1 | **数据真源** | `docs/notes/atlas/` 分层文档是唯一真源，物理图谱**单向生成**（改文档 → 图跟着变）。参数默认值/范围来自 `src/py21cmfast/wrapper/inputs.py` 的结构体；论文出处来自源码注释里**真实存在**的引用。 |
| 2 | **层级与粒度** | 骨干 = **16 个阶段**（S01–S16，含 Python 侧装配/编排/缓存）；下钻 = **71 个子过程**；**208 个计算单元不画成节点**，只作「实现落点」（文件 + 符号 + 行区间）。 |
| 3 | **字段表** | 见下表。取值只来自文档与源码原文，**没有就留空**。 |
| 4 | **交付与边界** | 应用内第三页「物理图谱」；四路检索（参数 / 物理量 / 过程名 / 论文）+「看实现」一跳。**不做**审读批注、评估字段、可写标注（评估是使用者自己的工作）。 |

### 字段表（生成物契约）

| 字段 | 来源 | 缺失时 |
| --- | --- | --- |
| 作用与意义 | L1（阶段）/ L2（子过程）同名必答字段 | 留空 |
| 关键过程 | L4「关键过程」（按 `所属单元` 归到子过程） | 留空 |
| 关键量 | L4「关键量」 | 留空 |
| 输入 / 输出产物 | L1「输入产物 / 输出产物」（→ P 编号与名称）；子过程见 L2「输入 / 产出」 | 留空 |
| 上游 / 下游阶段 | 由产物边推导 | 留空 |
| 负责入口 | L1「负责入口」（→ E 编号） | 留空 |
| 实现落点 | L3「承担者」→ 源文件 + 符号 + **函数体行区间**（脚本定位） | 留空并记日志 |
| 涉及参数 | 沿用参数矩阵的归属口径（L3 承担者函数体里扫参数） | 空数组 |
| 论文出处 | 源码注释/文档字符串里的真实引用 + 引用点 `file:line` | 空数组 |

### 边口径

`L1` 的「输出产物」= 产者，「输入产物」= 消费者 ⇒ 边写成 `产出者 → 消费者`，**标签是产物名**（如「P02 初始条件」）。这样做的好处：沿用画布已有的"产物写在边标签上"读法（读者不需要重新学一套），且依据是文档里的权威字段，不靠脚本推断。自环不生成。

### 论文口径（这一条最要紧，也最容易做脏）

- **只抽**：源码注释与 docstring 里已经写着的引用。已核实形态规整且量足够——`src/py21cmfast` 共 **14 个文件、58 行**，例如
  `InitialConditions.c:747 // ZA reference: Scoccimarro R., 1998, MNRAS, 299, 1097-1118`、
  `cosmology.c:52 // … Eisenstein & Hu ApJ, 1999, 511, 5`、
  `cosmology.c:74-75 // Bardeen et al 1986 ApJ, 304, 15` + `// with baryon correction from Sugiyama 1995 ApJS 100, 281`、
  `LuminosityFunction.c:2 G. Sun and S. R. Furlanetto (2016) MNRAS, 417, 33`、
  `Stochasticity.c:501-502 Darkforest (Qiu et al 2020. ArXiv: 2007.14624)`、
  `wrapper/inputs.py` 的参数级引用（`HII_EFF_FACTOR … Eq. 2 of Greig+2015`、`M_TURN … See Sec 2.1 of Park+2018`、`USE_CMB_HEATING … Meiksin 2021, arxiv.org/abs/2105.14516`、`USE_LYA_HEATING … Reis+2021, doi.org/10.1093/mnras/stab2089`）、
  `utils.py` 里带 DOI/ADS 的完整条目。
- **MUST NOT**：补全残缺条目、猜期刊卷页、把"作者+年份"扩写成完整引文、凭印象推荐文献。抽不出就是空。
- **去重键**：作者-年份（小写规范化）；同一篇的多个引用点全部保留，因为它们正是"论文 → 代码"的检索路径。

## 二、为什么这么定（被否方案）

- **否：改造工程画布图本身**（把过程提级、把方法折下去）。工程图是开发者的地图，也是把每条结论钉回源码的凭据；动它会牵连话题、标签、大框、手摆坐标与既有断言。第三方视图的边际成本远低于改造它。
- **否：让物理图谱独立维护一份数据**（不生成）。那会立刻产生第三个真源，与文档、与矩阵三方漂移。
- **否：218 个计算单元全上节点**。一屏 200+ 个框与"快速上手"相反；计算单元的正确位置是"落点"，不是"路标"。
- **否：把论文做成手写文献表**。手写就等于我替你判断该引什么——这不是工具该做的事；源码注释里已有的引用才是可核查的事实。
- **否：加"审读批注/评估结论"字段**。用户明确说评估是他自己的活；工具加一个可写层，就会把"图是结论、不随手写"的既有原则冲掉。

## 三、落地结构

```
docs/notes/atlas（真源）  ┐
src/py21cmfast（参数结构 + 注释文献）  �├─→ scripts/build-physics-map.mjs ─→ src/generated/physics-map.json
                          ┘                                                  │
                                                          src/lib/physicsMap.ts（纯函数：模型 + 四路检索）
                                                                             │
                                          PhysicsMapView（阶段骨干 + 下钻 + 检索）├─→ PhysicsMapDetail（字段表 + 落点 + 文献）
                                                                             └─→ CodePreviewDrawer（看实现，高亮行区间）
```

- **分层与矩阵页一致**：真源 → 生成物 → 纯函数换算 → 视图。视图不解析文档、不读源码。
- **复用而不新造**：`scripts/lib/atlasDocs.mjs`（`loadAtlas()` / `parseEntries()` / `sourcePathOf()` / `codeSpans()`）、`scripts/lib/paramScan.mjs`（`findSymbolBodies()` / `scanParams()` / `readSource()` / `classifyKind()`）、`CodePreviewDrawer`、`StatusBar` 的双口径写法、视图隔离 effect 写法。
- **历史包袱要避开**：矩阵页数据源叫 `physics-graph.json`，本页叫 `physics-map.json`，两名字相近，故在所有新文件的头注释里写明"本文件对应第三页「物理图谱」，与矩阵的数据源 `physics-graph.*` 无关"。

## 四、风险

| 风险 | 处置 |
| --- | --- |
| 论文抽取误判（把普通注释当文献） | 只在**注释/字符串**里按"作者 + 年份 +（期刊卷页 或 arXiv/DOI）"的形态抽；自检回读被抽行核对，抽不到即空 |
| 落点行区间错位 | 只认 `承担者` 给出的符号，用现有函数体定位（C 按花括号、Python 按缩进）；自检校验行区间落在文件内 |
| 生成物被人手改 | 生成物头部写入 `source` 与内容哈希 `stamp`；自检重算哈希，不一致即失败 |
| 第三页重演"矩阵页残留选中" | 直接照抄已归档的隔离口径，并纳入浏览器探针 |
| 参数范围解析不稳（`between`/`gt` 多种写法） | 认不出就留空（MUST NOT 猜）；自检要求"至少 N 个参数能解析出默认值"，防静默全空 |
