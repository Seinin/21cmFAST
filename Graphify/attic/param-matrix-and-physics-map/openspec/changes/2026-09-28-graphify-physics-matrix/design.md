## Context

见 proposal.md 的 Why。现状与约束：

- 工程视角图谱 `data/graph.json` 由一串 `scripts/build-*.mjs` 生成、经 `apply-annotations.mjs` 合并；节点带函数名，
  参数标签由 `scripts/scan-param-tags.mjs` 按"节点 refs 所在函数体 ± 窗口"扫出。**本变更不动它**。
- `docs/notes/atlas/` 是一套四层文档栈（L0 产物 / L1 阶段 / L2 子过程 / L3 计算单元 / L4 关键量），
  L1 与 L2 明确声明"不出现函数名、文件路径、变量名"；每条都有统一的 `- **字段**：值` 结构，锚点是 GitHub slug。
- L3 的「承担者」字段给出实现该单元的函数/文件与源码链接——这是"参数落在哪个过程"的最可靠锚点。
- 前端是单页应用（无路由），现有 URL 只同步 `?g=<子图焦点>`。

## Goals / Non-Goals

**Goals:**
- 一份**可重跑的**物理视角图谱：过程名/描述来自文档原文，参数来自源码结构，归属来自计算单元的函数体。
- 一个**读法一致**的矩阵视图：沿用仓库既有"有色格 = 有关系、空格 = 无关"的约定，双向汇总。
- 与工程视角图谱彻底隔离：不同文件、不同生成脚本、不同视图，互不写对方。

**Non-Goals:**
- 不修工程视角图谱的参数归属（只在新图谱里用更准的口径），不改它的生成器、不重命名它的节点。
- 不手写参数说明与格子概述（那是"次级算法过程"那一层的活，本次只留挂载位置）。
- 不做筛选器/导出/画布视图（矩阵是新图谱的第一个视图，不是全部）。
- 不改服务端、不引入新依赖。

## Decisions

**D1：产物放 `src/generated/physics-graph.json`（入库跟踪），不放 `data/`。**
根 `.gitignore` 的 `data/` 规则会把任何层级的 `data/` 目录吃掉，产物放那里会导致构建期 import 缺文件。
放 `src/` 下还能被 `tsconfig` 的 `include: ["src"]` 覆盖（`resolveJsonModule` 已开）。
替代方案：放 `data/` 并让服务端多一个只读端点——但那要给一份静态数据加服务端代码，违背"不需要额外的工程要素"。

**D2：形状沿用 Graphify schema。**
好处有三：直接复用 `parseGraph` 做严格校验；将来给新图谱加画布视图/容器/**次级算法过程**（作为过程节点的子节点）不用改数据模型；
`check:physics` 与既有自检脚本能用同一套读取方式。
替代方案：自定义一份"矩阵专用"结构——更贴合当前页面，但把将来的层级扩展堵死。

**D3：过程列默认取 L1 的后端物理阶段（`S07`–`S15`，9 列）。**
文档本身把 S01–S05 划为 Python 侧、S06 是配置：那些阶段的"命中"要么是字段定义、要么是参数被传入，不是物理消费
（实测：`USE_TS_FLUCT` 在 `coeval.py` 的编排里出现多次，但那是传参）。`S16` 是"跨阶段基建与校准"，默认排除；
要含它、或要换成 71 个子过程粒度，用 `--stages=` / `--layer=subprocesses` 一把切换，不改代码。
替代方案：33 个旧图谱过程节点——名字带函数名，正是要摆脱的口径。

**D4：归属按 L3 承担者的函数体扫描，不用旧图谱的 refs。**
旧口径的窗口是 `min(引用行-2, 函数体起)` 到 `max(引用行+30, 函数体末)`：对 `global_evolution.py:110` 这个引用，
它一路盖到 27–140 行，于是把 65–72 行的电离效率公式一起吸进了"输出层"那个 artifact 节点——这就是那四个参数
（`F_STAR10` / `F_ESC10` / `HII_EFF_FACTOR` / `POP2_ION`）偏斜的成因。新口径只取**承担者符号自己**的函数体
（C 按花括号配对、Python 按缩进，先屏蔽注释与字符串），于是它们落回 `scaling_relations.c`（标度关系）、
`SpinTemperatureBox.c` 的全局电离历史、`IonisationBox.c` 的常数初始化、`heating_helper_progs.c` 的频率积分等真实环节。
承担者只写文件名或"各函数"时退化为整文件归属（生成日志列明），避免漏扫。
替代方案：复用 `scan-param-tags.mjs`——它是可执行脚本、不导出函数，且口径正是要改的那个。

**D5：戳记用内容哈希。**
schema 要求 `createdAt`/`updatedAt` 非空，但写当前时间就让幂等失效。改用内容哈希（`generated-<12 位>`）：
内容不变则产物逐字不变，内容变了自动跟着变，`check:physics` 直接以"重跑 `--stdout` 与磁盘文件逐字比较"断言幂等。

**D6：矩阵的"作用概述"用文档原文，不手写。**
格子给出角色词（入公式 / 赋值 / 开关）与"落在哪个子过程"（子过程名来自 L2 文档），物理描述在过程详情里给
L1 的「作用与意义」原文。用户已明确：真正的"作用概述"属于将来的**次级算法过程**层，本次不编造。

**D7：视图切换走 URL `?view=matrix`，与 `?g=` 并存。**
沿用现有 `window.history.replaceState` 的写法，零路由依赖。矩阵视图替换掉工作区（面板 + 画布），顶栏与状态条保留。

## Risks / Trade-offs

- [整文件归属可能把同文件里别的阶段的内容吸进来] → 只在"符号一个都没定位到"或"承担者明说各函数"时启用，且生成日志逐条列出；自检对锚点、出处、角色取值都做校验。
- [矩阵列粒度选粗了会看不出细节] → `--layer=subprocesses` 可切 71 列；格子文案里始终带子过程名，粗粒度列也读得出细节。
- [参数说明有 3 个源码里没写] → 如实留空（行头只显示参数名），自检把这几条列出来，不编造。
- [两个图谱在同一界面里可能被混淆] → 顶栏切换按钮的 tooltip 明写各自的数据文件；README 与 DESIGN 各记一节。
- [生成物入库会让 diff 变大] → 产物 35 KB、内容哈希戳记、只在文档/源码变化时变化。

## Migration Plan

无数据迁移：新图谱是新文件，首次生成即产出。回滚就是把视图切回画布（或删掉生成物与两个新页面组件）——
工程视角图谱与服务端不受任何影响。
