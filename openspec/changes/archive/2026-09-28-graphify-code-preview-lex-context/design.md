# 设计

## 两半，缺一不可

| 场景 | 现象 | 靠哪一半修 |
| --- | --- | --- |
| 连续读完文件，构造横跨段接缝 | 每 300 行一道接缝，接缝后整片变色 | 显示层按**连续区间**合并，一次词法分析 |
| 跳进文件中间，开引号从未进入内存 | 窗口里那个"本该是闭引号"的 `"""` 被当成开引号 | 服务端给一行**词法前缀**，前端拼上但不显示 |

## 决策与理由

### 为什么是「一个连续区间一次分析」，而不是「每段各补一次前缀」

每段各做一次分析，段间接缝必然无解（跨段构造在任一段里都缺另一半），同一份内容还会被反复分析。合并后 tokenize 的总行数不变、次数从"段数"降到"不连续区间数"，更快也更稳。跳转造成的空洞不硬拼：两段文本拼在一起会让接缝处凭空多出一对"开/闭"，比不合并更糟。

### 为什么前缀只给「开启构造的那一行」

三引号字符串与块注释的**内部在词法上是不透明的**：给出开引号那一行，状态就摆正了，后面的内容由窗口正文自己闭合，结果与整文件分析一致。实测印证：把 `    r"""` 那一行拼在 601–900 段之前，644 行立刻从"整片字符串"变回 `lightconer <span class="token">=</span> lightconer.validate_options(`。前缀体积因此是 **O(1) 一行**，而不是 O(窗口起点)。

### 为什么前缀行隐藏而不是显示

- 显示会让行号从 590 跳到 601（或反过来让窗口首行的行号变错）。
- 用户随后的向上续段会把上一段加载进来，同一行会出现两次，`code-line-N` 的 DOM id 也会撞——续段锚定、打开定位、跳转定位全靠它取元素。

### 行号口径（踩过的坑）

`react-syntax-highlighter` 的 `startingLineNumber` 是**顺序编号**，隐藏的前缀行照样占一格。若仍从 `startLine` 起数，后面每一行的编号都会被顶掉一位：探针实测 `code-line-644` 里装的其实是文件第 654 行，滚动定位与高亮区间全体错位。因此起点改为 `startLine - 前缀行数`——那一格正好被不显示的前缀行吃掉，**可见行**拿回真实行号。

### 为什么不做「把窗口起点回退到构造开头」

那样段与页边界不再对齐：相邻段可能重叠（`code-line-N` 会重复），且回退距离撞上单次上限 `CODE_MAX_WINDOW_LINES` 时窗口会盖不住请求区间（大注释块动辄上百行）。一行前缀没有这些问题。

### 词法状态机

`server/lib/lexState.mjs` 从第 1 行扫到窗口起点的前一行，跟踪：行注释（`#` / `//` / `!`）、块注释、三引号（含 `r` / `b` / `f` / `u` 前缀）、反引号模板串、单双引号串（转义与反斜杠续行）。规则按语言家族选：`python` / `toml` / `bash` 用 `#`+三引号，`c` / `cpp` / `css` 用 `//`+块注释，`javascript` / `typescript` / `tsx` 再加反引号，`fortran` 用 `!`（`//` 在那门语言里是字符串拼接），`json` / `text` 直接跳过。

已知不覆盖（不影响本仓预览）：shell 的 heredoc、JS 正则字面量里的引号/反引号、模板串 `${}` 插值内部再嵌字符串。

### 性能

- 服务端：只扫到窗口起点之前，O(窗口起点行数)；只对需要的语言家族启用。按 `path + mtime` 缓存"跨行构造区间表"是可选优化，本仓文件规模下没必要。
- 前端：每区间一次 tokenize（总行数不变），700 行量级在毫秒级；`mergeRuns` 是对已加载段的单趟合并。

## 兼容性

- 服务端字段与前端 prop 全部**增量**：既有响应字段、`CodeWindow` 既有字段、`readCode` / `readCodeRange` 的请求参数、抽屉与选择器的调用方式一律不变；`CodeSnippet` 保留原签名成为 `CodeBlock` 的薄封装。
- 触边判定与续段锚定继续以「段」（请求单位）为准：`code-line-${segment.segmentStart/End}` 依旧存在；`SegmentHint`（占高度的提示行）留在块之间，向上续段的补偿逻辑（等提示收走再补偿）不受影响。
