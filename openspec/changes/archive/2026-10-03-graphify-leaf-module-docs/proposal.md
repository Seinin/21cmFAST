## Why

两件事，都指向同一个毛病：**最底层不是物理，而是代码**。

其一，图上还有第三级——双击一个成员会展开它的"实现步骤"（18 个函数节点：`UpdateXraySourceBox`、`get_Ts`、`sum_halos_onto_grid`…）。物理链的底应当是**物理量与物理过程**，函数怎么切、怎么调是实现细节；再往下展开一层，一级（块）→ 二级（成员）→ 三级（函数）读下来，读者拿到的是代码结构图，不是物理链。函数那一层要的是"这个量由哪几行算出"，这件事在成员自己的代码落点与文档里就说得清。

其二，12 篇模块文档一篇一个块，物理节是 `1. 2. 3. 4.` 的编号条目——一个块里塞 5–6 个成员，读者读不到"这个量为什么这样算"；物理与工程只是前后摆放，没有逐条咬合。同时，图上最细的落点（成员量、共享内核层的 16 个头文件成员）在文档里**没有自己的位置**。这与本链既有的"成员最细、块 = 成员并集"口径直接矛盾。

## What Changes

- **删除第三级「函数子图」**（口径变更）：产物里 MUST NOT 再有 `step:*` 节点，`graph.subgraphs` MUST NOT 有「成员 → 步骤」这一层索引；步骤名 MUST NOT 出现在画布、属性页、成员明细、检索命中或「子图入口」计数里。实现步骤的核定落点并进它所属成员自己的代码引用；步骤名只留在该成员那篇文档的工程一节里（**这一部分只活在成员的代码与文档里**）。
- **「子图入口」只出现在块上**：成员一律不给入口（不许拿"有几个实现步骤"当它的子节点数）。
- **文档树与图同构**：每个对象按 `parent` 嵌套成目录，进入某个对象就读它那一段。
  - 块（12 篇）：一篇 md + 同名目录；正文 = **成员并集**（物理 = 各成员的物理环节按序并集，工程 = 各成员落点并集），自身不另写散文。
  - 成员（39 篇，图的终点）：一篇 md，写自己那一段；它的实现步骤在工程一节里各占一个小节。
  - 共享内核层的 16 个头文件成员：各一篇（不是图上节点，但是那一层的成员）。
- **每篇两节固定**：`## 物理` → `## 工程`。
  - 物理一节 MUST 是**成段叙述 + 不编号的小标题**（按物理环节分），段内给公式与推导；**每个成员恰好一个公式**（16 个头文件成员除外——它们不是可求值的量），多于或少于一个都判失败。
  - 工程一节 MUST 与物理一节逐条对齐：每个实现步骤给**核定的核心行**加一句说明，以及该成员的输入与产出。
- 真源新增 `docText`（键 = 对象 id，层里的头文件成员用 `file:<文件名>`），每个成员一条 `physics`（小标题 + 段落）与一条 `formula`；块的正文由生成器按成员并集算出，真源不重复写。
- **BREAKING**：`noteDoc` 从"每块一个"改为"每对象一个"（路径由 `parent` 关系推导：块与成员用各自标识，头文件成员用文件名；不再手写路径）；`blocks.items[].module.physics / products` 的块级编号条目退场；名字带「（子图）」的工程项（`hmf_impl`、`source_grid`）改名去掉这个后缀。
- 自检相应改造：**图上没有 `step:*`**；**文档路径与 `parent` 同构**（生成器与自检各实现一遍路径规则再对拍）；`docText` 的键集合 = 对象 ∪ 层成员，不重不漏；物理一节无代码痕迹；**每个成员恰好一个公式**；「子图入口」的计数判据只在块上非 0；引用汇总的最深一层改为成员并独立重算对拍。
- 口径账本同步：`docs/notes/physics-chain/README.md` §九「模块文档（位置与形状）」与 `design.md` 相应条目改写。
